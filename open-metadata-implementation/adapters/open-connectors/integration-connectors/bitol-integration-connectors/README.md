# The Bitol Connectors

The [Bitol](https://github.com/bitol-io) project publishes two open standards for describing data products and the
data they exchange:

* the **Open Data Contract Standard (ODCS)** - a YAML document (`kind: DataContract`) describing a dataset: its schema,
  data quality checks, service level agreement, support channels, pricing, team, access roles and the servers where it resides.
* the **Open Data Product Standard (ODPS)** - a YAML document (`kind: DataProduct`) describing a data product: the
  data it consumes (input ports) and provides (output ports), each described by an ODCS contract, plus its management ports, support channels and team.

The vocabularies of the standards (document status, logical types, quality check types, metrics, dimensions, severities and
comparison operators, semantic types, SLA drivers, server types, support tools and scopes, authoritative definition types,
management port content and types, and data product types) are Java enumerations in the OIF `bitol` packages.  The cataloguers
normalise the values they store through these enumerations, and the Core Content Pack registers the same values as
[valid metadata values](https://egeria-project.org/guides/planning/valid-values/overview/) for the properties they are stored
in (for example `checkType` and `comparisonOperator` on `DataQualityRule`, `dataType` on `DataField`, and the `bitol.semanticType`,
`bitol.type` and `bitol.content` additional properties), so that user interfaces can offer the standard choices.  Values outside
the standard are stored as written; none of the value sets is closed.

The beans follow **ODCS v3.2.0** and **ODPS v1.1.0** (September 2026).  Any ODCS v3.x document and any ODPS v1.x (or v0.9.x)
document is accepted; documents generated by Egeria carry the current version.  Values that the standards allow to be
variable references (`${VAR_NAME}` or `${VAR_NAME:-default}`, RFC 0050) are preserved verbatim, including a server `port`
written as a string.

Egeria's Open Integration Framework (OIF) provides beans for both documents (`org.odpi.openmetadata.frameworks.integration.bitol`)
and a distribution mechanism in the integration daemon that mirrors its support for Open Lineage events: an integration connector
may register a *Bitol listener* with its integration context to receive every document published to the daemon, and may publish
documents for the other listeners.  Documents may also be published to the daemon through its REST API (`publish-data-contract`
and `publish-data-product`) and through the Product Manager OMVS.

The connectors in this module are divided into two groups:

- the integration connectors that are acquiring Bitol documents (the *receivers*);
- the integration connectors that are processing or distributing them (the *cataloguers* and *stores*).

## Bitol Files Receiver Integration Connector

The Bitol Files Receiver integration connector monitors file directories - typically a git checkout, or a drop folder, where teams
publish their data contracts and data product descriptors - and publishes the new and changed documents to the Bitol listeners
registered in the same integration daemon instance.  On each refresh it scans the directory tree for `.yaml`, `.yml` and `.json`
files whose `kind` is `DataContract` or `DataProduct`.  Hidden directories such as `.git` are skipped, and a file is only
published again when its last modified time changes.

### Configuration

This connector runs in the [Integration Daemon](https://egeria-project.org/concepts/integration-daemon).  A directory to monitor
is supplied either in the `networkAddress` of the connection's endpoint, or as a *FileFolder* catalog target (catalog target name
`directoryToMonitor`).

```json
{
   "connection" :
                {
                    "class" : "Connection",
                    "qualifiedName" : "Egeria:IntegrationConnector:Bitol:FilesReceiver Connection",
                    "connectorType" :
                    {
                        "class" : "ConnectorType",
                        "connectorProviderClassName" : "org.odpi.openmetadata.adapters.connectors.integration.bitol.BitolFilesReceiverIntegrationProvider"
                    },
                    "endpoint" :
                    {
                        "class" : "Endpoint",
                        "address" : "{{folderName}}"
                    }
                }
}
```

- Replace `{{folderName}}` with the path name of the directory to monitor (for example the root of a git checkout).

## Bitol Event Receiver Integration Connector

The Bitol Event Receiver integration connector receives Bitol documents from an event topic - one complete YAML or JSON document per
event - and publishes them to the Bitol listeners registered in the same integration daemon instance.  It uses the
[Open Metadata Topic Connector](https://egeria-project.org/concepts/open-metadata-topic-connector) created for each *Topic* catalog
target (catalog target name `topicToMonitor`) to receive the events.

### Configuration

This connector runs in the [Integration Daemon](https://egeria-project.org/concepts/integration-daemon).

```json
{
   "connection" :
                {
                    "class" : "Connection",
                    "qualifiedName" : "Egeria:IntegrationConnector:Bitol:EventReceiver Connection",
                    "connectorType" :
                    {
                        "class" : "ConnectorType",
                        "connectorProviderClassName" : "org.odpi.openmetadata.adapters.connectors.integration.bitol.BitolEventReceiverIntegrationProvider"
                    }
                }
}
```

- Add the Kafka (or other) topic assets to monitor as catalog targets of the connector.

## Bitol Data Product Cataloguer Integration Connector

The Bitol Data Product Cataloguer integration connector registers a Bitol listener with the integration daemon and
catalogues each ODPS document it receives.  The mapping is performed by `DataProductMapper` in the Open Integration
Framework so that the same logic is available to the Product Manager OMVS.

| ODPS | Open metadata |
|---|---|
| document (one per version) | `DigitalProduct` with qualified name `DataProduct::{id}::{version}`, `identifier`, `versionIdentifier`, `productName`, `purpose`; the `id` is also an `ExternalId` shared by all versions |
| `status` | `contentStatus` (`proposed`, `draft`, `active`, `deprecated`); a `retired` product is soft-deleted |
| `domain` | a `DigitalProductCatalog` that the product is a member of |
| `tenant` | an `Organization` that the product is scoped by (`ScopedBy`) |
| `tags` | search keywords |
| `inputPorts`, `outputPorts` | `SolutionPort`s (direction input/output) of a `SolutionComponent` that is a member of the product; an output port whose `contractId` is already catalogued becomes an `AgreementItem` of that agreement |
| `managementPorts` | `Endpoint`s listed as resources of the product (`ResourceList`) |
| `support` | `ContactDetails` linked by `ContactThrough` |
| `team` | a `Team` profile scoped to the product; each member a `PersonRole` scoped to the product and appointed to the person's profile when the username is known as a user identity |
| `authoritativeDefinitions` | `ExternalReference`s linked by `ExternalReferenceLink` |
| `type`, `deprecated` (ODPS v1.1.0) | `bitol.type`, `bitol.deprecated` additional properties on the product; `deprecated` on ports and management ports likewise on the port or endpoint |
| `synonyms`, `context` (ODPS v1.1.0) | kept in full as JSON in `bitol.synonyms` and `bitol.context` on the product and on the output port |
| `outputPorts[].sbom[]` (with tags, custom properties and authoritative definitions) | kept in full as JSON in `bitol.sbom` on the port |
| `customProperties[].vendor` | the custom property is still a plain additional property; when any entry has a vendor, description or id the full list is also kept as JSON in `bitol.customProperties` |
| `customProperties`, `description.limitations`, `description.usage` and anything else without a home | `additionalProperties` (prefix `bitol.`) |

Anything the connector could not fully represent (a team member without a user identity, a contract not yet
catalogued) is reported in the audit log and recorded in the element's additional properties so that republishing the
document once the missing element exists completes the links.

### Configuration

This connector runs in the [Integration Daemon](https://egeria-project.org/concepts/integration-daemon).

```json
{
   "connection" :
                {
                    "class" : "Connection",
                    "qualifiedName" : "Egeria:IntegrationConnector:Bitol:DataProductCataloguer Connection",
                    "connectorType" :
                    {
                        "class" : "ConnectorType",
                        "connectorProviderClassName" : "org.odpi.openmetadata.adapters.connectors.integration.bitol.DataProductCataloguerIntegrationProvider"
                    }
                }
}
```

## Bitol Data Contract Cataloguer Integration Connector

The Bitol Data Contract Cataloguer integration connector registers a Bitol listener with the integration daemon and
catalogues each ODCS document it receives.  The mapping is performed by `DataContractMapper` in the Open Integration
Framework so that the same logic is available to the Product Manager OMVS.

| ODCS | Open metadata |
|---|---|
| document (one per version) | `Agreement` classified `DataSharingAgreement`, qualified name `DataContract::{id}::{version}`, `identifier`, `versionIdentifier`, `purpose`; the `id` is also an `ExternalId` shared by all versions |
| `status` | `contentStatus`; a `retired` contract is soft-deleted |
| `tenant` | an `Organization` that the agreement is scoped by (`ScopedBy`) |
| `tags` | search keywords |
| `schema[]` | a `DataStructure` per schema object, an item of the agreement (`AgreementItem`); `namespacePath` = physical name |
| `schema[].properties[]` | a `DataField` per property (`MemberDataField`), nested properties and array items as nested fields (`NestedDataField`); `dataType` = logical type, `isNullable` = not required, `allowsDuplicateValues` = not unique, `isPartitionKey`/`partitionKeyPosition`, `minimumLength`/`length` from the logical type options |
| `primaryKey`, `classification`, `criticalDataElement` | `PrimaryKey`, `Confidentiality` (public, internal, confidential, sensitive, restricted) and `Criticality` classifications on the field |
| `relationships` | `LinkedDataField` between the fields (shorthand `object.property` references within the contract; `contractId.object.property` references to the latest catalogued version of another contract) |
| `quality[]` | a `DataQualityRule` per check (dimension, type, metric, comparison operator and thresholds, severity, business impact, schedule, engine, expression) governing the structure or field (`GovernedBy`) |
| `slaProperties[]`, `description.limitations`, `description.usage` | a `ServiceLevelObjective` governing the agreement: SLA properties as obligations, limitations as restrictions, usage as entitlements |
| `servers[]` | `Endpoint`s listed as resources of the agreement (`ResourceList`), with the type-specific location fields in additional properties |
| `roles[]` (contract and server level) | a `SecurityAccessControl` governing the agreement, with a `SecurityRole` per role linked by `AssociatedSecurityList` whose `operationName` is the ODCS `access` value; approvers (and the server for server-level roles) in additional properties |
| `team`, `support`, `authoritativeDefinitions` | as for data products |
| `logicalType: map` (ODCS v3.2.0) | the key and value definitions become nested fields of the map field (`NestedDataField`, qualified names ending `::key` and `::value`), in the same way as array items end `::items` |
| `logicalType: vector` and its options (ODCS v3.2.0) | `dataType` = `vector`; `dimensions`, `elementType`, `distanceMetric`, `normalized`, `embeddingModel` and `embeddingModelVersion` as `bitol.` additional properties |
| `enum` (ODCS v3.2.0) | kept in full as JSON in `bitol.enum` on the field |
| `semanticType` (ODCS v3.2.0) | `bitol.semanticType` on the field (`measure` and `dimension`; absent for a plain column) |
| `synonyms` (ODCS v3.2.0) | `aliases` on the data field, plus the full list (locale, source, status) as JSON in `bitol.synonyms` on the field or structure |
| `deprecated` (ODCS v3.2.0) | `bitol.deprecated` on the field or structure |
| `context` (ODCS v3.2.0) | kept in full as JSON in `bitol.context` on the agreement and on the structure |
| `relationships[].id` | `bitol.id` on the `LinkedDataField` relationship |
| `slaProperties[].customProperties` and `authoritativeDefinitions` | carried in the lossless `bitol.slaProperties` JSON on the service level objective |
| `servers[].encoding` and the new server types (`hana`, `iceberg`, `exasol`, `teradata`, Actian) | additional properties of the endpoint, as for the other server fields |
| `price`, `dataProduct`, `contractCreatedTs`, `customProperties` and anything else without a home | `additionalProperties` (prefix `bitol.`) |

### Configuration

This connector runs in the [Integration Daemon](https://egeria-project.org/concepts/integration-daemon).

```json
{
   "connection" :
                {
                    "class" : "Connection",
                    "qualifiedName" : "Egeria:IntegrationConnector:Bitol:DataContractCataloguer Connection",
                    "connectorType" :
                    {
                        "class" : "ConnectorType",
                        "connectorProviderClassName" : "org.odpi.openmetadata.adapters.connectors.integration.bitol.DataContractCataloguerIntegrationProvider"
                    }
                }
}
```

Publish data contracts before the data products that reference them, so that the products' output ports can be linked
to the agreements; a product published first records the contract identifier and is completed when it is republished.

## Bitol Document Publisher Integration Connector

The Bitol Document Publisher integration connector is the outbound side of the Bitol support.  It generates an ODPS document
for each digital product, and an ODCS document for each data sharing agreement, in open metadata and publishes them to the Bitol
listeners registered in the same integration daemon - typically the File-based Bitol Store, which writes them to a directory
ready to be committed to git.  The generators reverse the mappings used by the cataloguers, so a document that has been
catalogued can be regenerated, and products and agreements created through Egeria's own APIs (for example the Product Manager OMVS)
can be exported in the Bitol formats.

Documents are generated when the connector receives an event describing a change to a `DigitalProduct` or to an `Agreement`
classified as a `DataSharingAgreement`, and on each refresh for every product that is a member of a `DigitalProductCatalog`
attached as a catalog target (together with the contracts referenced by the product's ports).  A document is only published
when its content differs from the last document generated for the same element, so a cataloguer running in the same daemon
does not cause an endless exchange of identical documents.

The same generation is available synchronously through the Product Manager OMVS
(`GET .../digital-products/{digitalProductGUID}/data-product-document` and `GET .../agreements/{agreementGUID}/data-contract-document`)
for callers that want the document returned rather than published; the Product Manager OMVS also offers synchronous import
(`POST .../data-products/import-document` and `POST .../data-contracts/import-document`) that catalogs a document directly
and returns the unique identifier of the resulting element.

### Configuration

This connector runs in the [Integration Daemon](https://egeria-project.org/concepts/integration-daemon).  It needs no endpoint.
Digital product catalogs whose members should be regenerated on each refresh are attached as catalog targets
(catalog target name `productCatalog`).

```json
{
   "connection" :
                {
                    "class" : "Connection",
                    "qualifiedName" : "Egeria:IntegrationConnector:Bitol:DocumentPublisher Connection",
                    "connectorType" :
                    {
                        "class" : "ConnectorType",
                        "connectorProviderClassName" : "org.odpi.openmetadata.adapters.connectors.integration.bitol.BitolDocumentPublisherIntegrationProvider"
                    }
                }
}
```

## File-based Bitol Store Integration Connector

The File-based Bitol Store integration connector writes every Bitol document published in the integration daemon to the file system.
Each document is stored as `{{folderName}}/{kind}/{id}/{version}.yaml` (or `.json` when the document arrived as JSON), so the store
can be committed to a git repository as it stands.  Documents that could not be parsed are kept under
`{{folderName}}/{kind}/unparsed/`.

### Configuration

This connector runs in the [Integration Daemon](https://egeria-project.org/concepts/integration-daemon).  The directory to write
to is supplied in the `networkAddress` of the connection's endpoint, or as an *Endpoint*, *Connection* or *FileFolder* catalog target
(catalog target name `storeDirectory`).

```json
{
   "connection" :
                {
                    "class" : "Connection",
                    "qualifiedName" : "Egeria:IntegrationConnector:Bitol:FileBasedBitolStore Connection",
                    "connectorType" :
                    {
                        "class" : "ConnectorType",
                        "connectorProviderClassName" : "org.odpi.openmetadata.adapters.connectors.integration.bitol.FileBasedBitolStoreProvider"
                    },
                    "endpoint" :
                    {
                        "class" : "Endpoint",
                        "address" : "{{folderName}}"
                    }
                }
}
```

- Replace `{{folderName}}` with the path name of the folder where the files will be located.
