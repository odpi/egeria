# Messages and Codes

This utility generates the [messages-and-codes](../../../messages-and-codes) documentation at the root of the
repository.  That documentation describes every message that Egeria can produce - the messages that fill out
its exceptions, the messages written to its audit log destinations, and the notifications it sends.

## How it works

Egeria's messages are defined in *message sets* - java enums that implement one of the interfaces in the audit
log framework's
[org.odpi.openmetadata.frameworks.auditlog.messagesets](../../../open-metadata-implementation/frameworks/audit-log-framework/src/main/java/org/odpi/openmetadata/frameworks/auditlog/messagesets)
package:

* `ExceptionMessageSet` - messages that fill out the exceptions thrown by Egeria.
* `AuditLogMessageSet` - messages written to the audit log destinations.
* `MessageSet` - general purpose messages, such as the notifications sent to a subscriber.

The values in each message definition are literal constants in the enum's source, so this utility reads them
straight out of the source tree rather than loading the classes.  That means the documentation covers every
message set in the repository - including those in modules that are not part of the OMAG Server Platform
assembly - without this module needing a dependency on each of the 100+ modules that define one.

A message definition may also supply a **url** - a link to the page that describes the component or concept
the message is about.  It is the last value of the message definition and it is optional, so a message with no
suitable page to point at simply leaves it off:

```java
    NULL_URL(400, "POSTGRES-CONNECTOR-400-001",
             "Connection {0} has been configured without the URL to the database",
             "The connector cannot start because the endpoint of its connection has a null address property.",
             "Update the connection's endpoint to include the connection string needed to connect to the database.",
             "https://egeria-project.org/egeria-solutions/leveraging-postgres/overview/"),
```

The url is carried on `MessageDefinition`, so it travels with the message at runtime as well as appearing in
these pages:

* `AuditLog` copies it into the `messageURL` of every audit log record, so it reaches the audit log
  destinations - including the `message_url` column of the PostgreSQL audit log store, which existing
  deployments pick up as an `ALTER TABLE` when the server restarts.  The console destination prints it
  under the record for the severities that report a problem.
* The exception base classes record it as `reportedURL`, and `RESTExceptionHandler` carries it out in the
  `exceptionURL` of the error response and puts it back on the exception the client rebuilds - so a caller
  on the far side of a REST call still gets the link.

It is shown under **Further reading** on the generated pages.  When every message in a set points at the same
page - which is the common case, because the whole set belongs to one component - the link is shown once at
the top of the page rather than repeated under every message.

Point the url at a page on [egeria-project.org](https://egeria-project.org) or in the
[Egeria repository](https://github.com/odpi/egeria).  Check that the page exists before adding it: the docs
site publishes a [sitemap](https://egeria-project.org/sitemap.xml) that lists every page it has.

The parser is deliberately strict.  If it meets a message set that it cannot read it throws a
`MessageSetParsingException` and the build fails, rather than the documentation quietly losing a message.  It
also fails the build if the same message identifier is used by two different message sets, because that would
leave a reader unable to tell which situation their log record describes.

## Running it

The documentation is regenerated by the build:

```bash
./gradlew :open-metadata-resources:open-metadata-dev-utilities:messages-and-codes:generateMessageDocumentation
```

The task also runs as part of a normal `./gradlew build`.  The generated pages are checked in so that they can
be read and searched from GitHub, and only the pages whose content has actually changed are rewritten - so a
build that changes no messages leaves the working tree clean.  Pages left behind by a message set that has
since been renamed or removed are deleted.

The generator can also be run directly.  It takes the root of the repository and the directory to write to:

```bash
java -cp build/classes/java/main org.odpi.openmetadata.reports.messages.MessagesAndCodesReport . ./messages-and-codes
```

## Adding a new area to the documentation

The message sets are grouped into directories that match the part of Egeria that defines them.  The grouping
is held in
[MessageSetCategory](src/main/java/org/odpi/openmetadata/reports/messages/MessageSetCategory.java), which maps
a source path prefix to a documentation directory, a display name and a description.  Add a value to that enum
when a new area of Egeria starts defining messages - the categories are tested in declaration order, so a more
specific path prefix must be declared before a more general one.
