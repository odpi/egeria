# Transport Level Security in Egeria & Certificates

The Egeria applications need a truststore and a keystore to communicate securely.
The truststore keeps the list of certificates for trusted servers and the keystore defines the certificate information that the server sends out.

The `gensamplecerts.sh` script is used for generating self-signed certificates for the OMAG Server Platform, Egeria UI Platform and REACT UI presentation server.
Once the certificates are created, the script copies them into the right locations to be picked up by the build.

- The root directory for egeria gets the `truststore.p12` and the `keystore.p12` for the OMAG Server Platform.  This is copied into the distributions when the assembly is created.
- The same truststore and the specialized keystore for the Egeria UI Platform are copied into `egeria/open-metadata-implementation/user-interfaces/ui-chassis/ui-chassis-spring/src/main/resources` which results in them being included in the jar file for this application.

## Set up to run

The `gensamplecerts.sh` script uses `openssl`.  The default version for Linux is ok, but the version on the Mac is `libressl` by default and you need to use `brew install openssl@3` to install the genuine openssl library and then:

```bash
$ export PATH="/opt/homebrew/opt/openssl@3/bin:$PATH"
$ ./gensamplecerts.sh
```

The next time you run the build, the new certificates are incorporated in the distribution.

After running the script, be sure to check in all the updated files into GitHub since they contain counts.

It is possible to reset all the counts by setting CA_CLEAN environment variable.  However, this should not be the normal process. 

## Why certificate generation is not part of the build

`gensamplecerts.sh` is a manual step, run and checked in occasionally - it must not be wired into the Gradle build or a Docker image build so that it runs automatically every time. Two reasons:

- **Reproducible builds.** The generated keystores/truststores are binary content of the build output. If they were regenerated on every build, the same commit would produce a different, non-reproducible artifact each time it was built, making it impossible to verify that a released artifact matches the source it was built from.
- **Shared trust across containers.** All the certs generated by one run of the script are signed by the same `EgeriaRootCA`/`EgeriaIntermediateCA`, which is why a platform's `keystore.p12` and another component's `truststore.p12` trust each other. If each container/image in a distributed deployment (eg the OMAG Server Platform and an Engine Host running in separate Docker images) regenerated its own certs independently at build time - especially with `CA_CLEAN` - each would mint its own root CA, and the containers would stop trusting each other's certificates entirely. Certificates must be generated once, from a single run of the script, and then distributed consistently to every component that needs to trust them.

Regenerate only when needed (eg to add a hostname to `SAN`, or because the existing certs are approaching their expiry date), and always check in the result as described above.

## Using the certificates

Refer to the [admin guide documentation](https://egeria-project.org/guides/admin/configuring-the-omag-server-platform) for information on using the examples in this directory.

**Note:** Any generated certs are provided as an example only and to support demos and must not be used for production.  They are issued with `localhost`, `host.docker.internal` and `127.0.0.1` as subject alternative names (see `SAN` in `gensamplecerts.sh`) so they also work when a platform is run in a Docker container and addressed from other containers via `host.docker.internal`.  For any other hostname (eg a real distributed deployment) add it to `SAN` and regenerate.
